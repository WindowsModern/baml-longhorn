## 已完成的内容

### 两种记录框架、八个世代剖面

直接还原自反编译源码，而非猜测：

| 框架 | 世代 | 记录结构 | 下一记录规则 |
|---|---|---|---|
| **SHORT** | 4074、4083、4093 | `[int16 类型]`，**仅**可变大小记录有 `[int32 大小]` | `记录起点 + 2 + 大小` |
| **LONG** | 3683、3718、4015、4033、4039、4042 | `[int64 大小][int16 类型]` | `记录起点 + 大小` |

两种框架**互斥**：一者读类型字段的位置，另一者读的是「长度的低半部分」。
「下一记录」规则来自写入器——SHORT 谱系中 `BamlVariableSizedRecord.Write` 在写完类型
**之后**才执行 `num += 2`，因此**大小字段不包含类型字段**。

枚举演化是**实测**而非假设：

```
3683  23 个成员        4039  33 个成员        4083  34 个成员（与 4074 完全相同）
3718  25 个成员        4042  33 个成员        4093  37 个成员
4015  26 个成员        4074  34 个成员
4033  28 个成员
```

### 世代判别

不同世代的程序集报告**完全相同的文件版本**，却在字节层面互不兼容，
因此版本字符串毫无用处。判别依据是结构：

* **SHORT 家族** —— `FormatVersion` 元组：4074/4083 为 `(0, 0)`，4093 为 `(0, 1)`，
  AvalonCTP 为 `(0, 2)`。
* **LONG 家族** —— **根本不存在**该元组；按形状检测。

`BamlDetector.MinConfidence = 100`，因此**部分匹配即拒绝**，绝不会给出自信的错误解析。
这一点非常具体地重要：把 4093 的字节流交给 4074 读取器，它能撑过数条记录，
然后死在 `type 33` 上——该码在 4093 中是 `ResourceInfo`，在 4074 中是 `LastRecordType`。

判别实测：

```
samples/xaml          103 个文件   103 个识别为 4074    （100%）
samples/wcp4093       133 个文件   133 个识别为 4093    （100%）
HelloWorld-AvalonCTP    1 个文件     0 个识别            （正确拒绝）
```

### 4093 的载荷差异

4093 **不是**「记录更多的 4074」。对运行期序列化代码做差异比对后，发现**五个文件不同**，
其中**三处改变字节格式**：

| # | 发现 | 朴素读法的后果 |
|---|---|---|
| 1 | **`BamlTypeInfoRecord` 把 `TypeInfoFlags` 打包进承载 `AssemblyId` 的那个 `Int16` 的高 4 位；低 12 位才是 id** | 把 id 为 `0` 报成 `assemblyId=4096` |
| 2 | **`BamlAttributeInfoRecord` 在 `OwnerTypeId` 与 `Name` 之间插入一个 `BamlAttributeUsage` 字节** | 在下一条记录处失步 |
| 3 | **`AttributeInfo` 位于码 33 且为可变大小**（4074 中它在 32） | 4 字节大小字段被读成 2 字节载荷 |
| 4 | **`PropertyResourceReference`（码 35）为可变大小**——它派生自 `BamlPropertyRecord`，进而派生自 `BamlVariableSizedRecord` | 4 字节之后失步 |
| 5 | 新增四条记录：`DefArrayStart`、`DefArrayEnd`、`ResourceInfo`、`PropertyResourceReference` | 未知码 |

第 3 与第 4 项最具启发性。**尺寸分类错误是这种格式里代价最高的一类错误**：
把真正的 4 字节大小字段读成 2 字节载荷**不会立即失败**——错位后的字节**常常看起来又是合法的记录码**，
于是走查能**继续数百条记录才崩溃**。这正是**把尺寸问题伪装成载荷问题**的原因。

### 反编译器

两种谱系现在都输出**真正的 XAML**，而非调试转储。

* **SHORT** 通过 `ElementStart.TypeId` 解析元素名，其中**负值**索引 `BamlMapTable._knownTypes`；
  属性则通过 `Property.AttributeId` → `AttributeInfo.Name`。
* **LONG** 将 `Element.Id` **直接**对 `TypeInfo.TypeId` 查表，**没有负值编码**；
  而 `ClrObject.Id` **共用同一 id 空间**——这一事实是在一份本来正确的文档里
  产出六个无意义的 `clr#N` 标签之后才被发现的。

命名空间处理是**有意不同**的，且经过验证而非假设：4074 写出
`xmlns="http://schemas.microsoft.com/2005/xaml/"` 并可使用短名；而 4015 只写一条
`using:` 指令列出 CLR 命名空间，并用**完整类型名**引用一切。
较早的格式**纯粹面向 CLR**；URI 命名空间与前缀机制是**后一代**才引入的。

### 最重要的那个缺陷

`ComplexDynamicProperty` 开启一个嵌套作用域，由 `EndComplexDynamicProperty` 关闭。
把它当作**空属性**处理会产出 `<Fill>` 却**从不写闭合标签**，
于是作用域内的一切都挂到了**外层元素**而非该属性上。

它在 `481.baml` 中**静默丢弃了 111 个子树**；而**极其关键**的是——
**输出仍然是格式良好的 XML，且看起来完全合理**。它**不可能靠肉眼检查发现**。

它是被一条**不需要任何格式知识**的结构断言抓住的：

```
example.baml   open=3    close=3    selfclosed=0     balanced=YES
481.baml       open=648  close=300  selfclosed=348   balanced=YES
```

修复前 `481.baml` 是**不配平**的。该检查已保留为回归断言。

随后**主动搜寻**而非被动等待同一类缺陷：发现 `ClrArrayProperty`、`IListProperty`
与 `IDictionaryProperty` 存在**完全相同的漏洞**，并以同样方式修复——尽管**没有任何样本**会触发它们。

### 验证

| 语料 | 文件数 | 结果 |
|---|---|---|
| `samples/xaml`（4074） | 103 | **103 / 103** 完整 |
| `samples/wcp4093`（4093） | 133 | **133 / 133** 完整 |
| `samples/extracted-4093` | 5 | **5 / 5** 完整 |
| `example.baml`（3683，LONG） | 1 | 完整，标签配平 |
| `481.baml`（4015，LONG） | 1 | 完整，标签配平，2,149 条记录 |

值解码：4074 为 **99.98%**（5,660 / 5,661），4093 为 **99.99%**（6,802 / 6,803）。
两者各余 1 项均为**已知假阳性**——一个字面上就是 `23 17` 的 BAML 字符串，
即一个以文本承载的 `Point` 值。

4093 的值编码是**经过查证**（而非假设）与 4074 相同的，因为其记录载荷确有差异。
4093 反编译源码中的 `XamlLengthSerializer.ConvertCustomBinaryToObject`
与读取器从 4074 实现的**打包标签/宽度算法完全一致**，因此**无需新增解码器**。

## 尚未验证的部分

**夸大覆盖率的反编译器比一个声明自身边界的更糟。**

1. **构建 3718、4033、4039、4042 没有任何样本。** 其剖面可解析，且 LONG 写入器对整个谱系通用，
   但**没有任何真实字节检验过它们**。已通过对每个构建中所有程序集做 `.baml` 资源名扫描、
   清单普查，以及对最有希望的那个候选程序集做第二次独立复核来确认。
   这是**可用素材的缺口**：剖面表与写入器**无需改动**即可消费此类文件。
2. **4093 语料不存在对应的源 XAML**，因此它经过完整性与自洽性验证，
   但**未与「编译自」的源文件做过比对**。
3. **`GenericAttribute`** 渲染为 `{uri}local` 而非带前缀的名字。合法且无损，
   但它在样本中出现 **0 次**，因此任何前缀方案都**无法验证**。
4. **集合属性**已处理，但**无任何样本测试**——与第 1 项同属预防性。

曾尝试对未声明的 LONG 字节流做**字节签名扫描，并判定其不可用而放弃**：
`[int64 大小][int16 类型]` 在普通 PE 数据中**频繁误匹配**，假阳性远多于信号。
这一**否定性结论已被记录**，以免日后重复。

## 曾经错误、以及如何被纠正的结论

记录于此，因为**方法比具体发现更重要**。

| 错误结论 | 被什么推翻 |
|---|---|
| 「`481.baml` 的剖面是 3718」 | 码 24 从 4015 起才是 `DynamicPropertyCustom`；在 3718 中它是 `LastRecordType` 哨兵，无实现类。实测：3683/3718 在 9 条记录后失败，4015+ 走完 2,149 条到 EOF。 |
| 「`DefAttribute` 之前缺 4 字节」 | 手工推字节。而「**声明结束 vs 按字段读到的位置**」逐记录对照表显示**所有记录都吻合**——故障在别处。 |
| 「`ElementStart` 没有载荷」 | 同样是手工推字节。反编译源码写着 `RecordSize = 2` 与 `ReadInt16()`。 |
| 「`ClrObject` 没有自己的名字」 | 它静默产出了六个无意义标签。`ClrObject.Id` **共用** `TypeInfo` 的 id 空间。 |
| 「`ar-SA` 会让窗体崩溃」 | 在**同一个进程内构造了四个窗体**。把每种语言放进**独立进程**才证明那是探针假象——但这次排查**确实暴露了构造函数路径中两处未加保护的索引访问**，随后被修复。 |

教训是一致的：**手工推演原始字节产生了四次错误结论，
而机械化的逐记录对照表第一次就找到了真相。** 该对照表现已成为**定位任何未来失步问题的
标准方法**，并已写入文档。
